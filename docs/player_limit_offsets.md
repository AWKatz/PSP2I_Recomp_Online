# PSP2i's 4-player limits: addresses and offsets (Task 3.1)

This is a map of where the game assumes at most 4 players, for Phase 3 (raising the limit in hubs). The addresses are in the game's own executable (`NPJH50332` `EBOOT.BIN`) and are also the names of the recompiled functions: `08A70A50` is `psp_func_08A70A50` in `build/gen`.

**How it was found.** Ghidra wasn't used. The work was done with:
- the recompiler's disassembly, indexed by [port/re/xref.py](../port/re/xref.py), which tracks calls, data references, strings and pointer tables;
- the game's own debug strings (class names such as `TPartyOrgCtrlPSP`, and source paths);
- live memory snapshots of the running game ([port/re/ramdump.py](../port/re/ramdump.py); run with `PSP2I_RAMDUMP=1` and press F7).

The tables at the end are generated by [port/re/player_limits.py](../port/re/player_limits.py) and can be rebuilt with it.

**Confidence levels**
- **Confirmed:** read in the code and checked in live memory.
- **Code:** clear from the code alone.
- **Candidate:** a 4-element array whose purpose isn't established yet.

## 1. The party member table

`0x08ED5A28` holds a pointer to the party context, which is allocated on the game's heap (it was at `0x0904BBE0` in the snapshot below). It contains:

| Offset | Size | Meaning |
| --- | --- | --- |
| `+44` | 4 × 116 | the member slots |
| `+1644`, `+1645`, `+1646` | bytes | your own slot and party state. `08A705BC` returns `+1646`, and `08A71528` compares `+1645` with each slot. |

Each 116-byte member slot (offsets relative to the slot):

| Offset | Size | Meaning (from the accessors) |
| --- | --- | --- |
| `+0` | u32 | flags (`0x10000` for your character) |
| `+2`, `+4` | u16, u32 | identity: `08A70A98` matches members by these two fields |
| `+8` | … | member data: `member_data(i)` returns `slot + 8` |
| `+72` | u8 | (1 in every slot) |
| `+74` | u8 | **in use** |
| `+75` | u8 | (1 for your character) |
| `+84` | u32 | the member's current area or session, compared before returning the object id |
| `+100` | u32 | the member's **object id** (`0xFFFFFFFF` for an empty slot) |

**Accessors.** Every one checks `(u8)i < 4` before computing `ctx + 44 + i × 116`:

| Function | Does |
| --- | --- |
| `08A70A50` | member(i): the slot if it's in use, else NULL |
| `08A700CC` | member_or_default(i): the slot, or the shared empty member at `0x08ED95C4` |
| `08A714DC` | member_data(i): `slot + 8` if it's in use |
| `08A701F4` | member_object_id(i): the member's object id in the current area, else −1. Used by about 40 AI functions. |
| `08A70550` | slot_of(object id): which slot holds an object id (it's behind the script command `get.party_member_id`, script table entry at `0x08E94C58`) |

**Checked in live memory.** In the Episode 1 lobby, alone, the slots read:

```
[0] +0=10000 +72=1 +74=1 +75=1 +100=0
[1] +72=1   +74=0 +75=0 +100=FFFFFFFF
[2] +72=1   +74=0 +75=0 +100=FFFFFFFF
[3] +72=1   +74=0 +75=0 +100=FFFFFFFF
```

That's one member in use, in slot 0, with the other three empty, exactly as the code implies. This snapshot only shows a party of one. A capture with 2 to 4 members, once a second client can join (Task 3.2), should confirm the remaining slot fields.

## 2. Checked in a live party (two clients over the server)

Snapshots of Client A (party leader, host) and Client B (member) in the Multi Mode lobby, 60 fps, through `psp2i_server` (`PSP2I_RAMDUMP=1`, F7 in each window).

**Party member table.** Both clients hold the same two members in the same slots:

```
[0] +0=120000 +2=12 +4=3E8 +72=1 +74=1 +75=1 +84=1EAB90 +100=1      (Client A, the leader)
[1] +0=120000 +2=12 +4=3E9 +72=1 +74=1 +75=1 +84=1EAB90 +100=0      (Client B)
[2] +0=0      +2=0  +4=0   +72=1 +74=0 +75=0 +84=0      +100=FFFFFFFF
[3] +0=0      +2=0  +4=0   +72=1 +74=0 +75=0 +84=0      +100=FFFFFFFF
ctx+1644..1646: A = 00 00 00, B = 00 01 00
```

This corrects and extends section 1:
- `+4` is the member's party id: 1000 (`0x3E8`) for the leader, 1001 for the next member, in join order.
- `+75` is 1 for every member in use, not only for your own character (the solo capture could not tell them apart).
- `+0` is `0x120000` for members of a network party (`0x10000` alone).
- `+84` is the same for every member: the shared area or session.
- `+100` is each member's object id in the current area; the two clients agree on it.
- `ctx + 1645` is **your own slot**: 0 on the leader, 1 on the member.

**Network tables (row 6).**

| Table | Leader (host) | Member | What it is |
| --- | --- | --- | --- |
| `0x08EE0F40`, 4 × 16 bytes | slots 0 and 1 in use: `{1, buffer, buffer + 0x2040, 0x2000}` | all zero | The host's buffers per connection: an 8 KB pair each (the game's PTP sockets ask for 8224-byte buffers). **A 4-connection limit on the host**, so it must grow with the party size. |
| `[0x08EE0FC0]`, 4 × 260 bytes | one record in use (an object, vtable `0x08E81A90`) with two players | null pointer | One record for a party of two: per room or session, not per player. |
| `0x08EE0D98`, 4 pointers | empty | empty | Not used in Multi Mode: most likely the online (infrastructure) mode. |

**Matching (rows 2 and 3).** The logs show `sceNetAdhocMatchingCreate(mode 1, max 4, …)` on the host and `(mode 2, max 4, …)` on the member, and `0x08EDAF2C` reads 4 on the host.

## What this means for Task 3.2

- **Party table:** raising the party size needs two things. The table itself has to move to a bigger allocation, since `ctx + 44 + 4 × 116` ends at `+508`, and the party code uses fields from `+508` to `+548` right after it, plus more up to `+1860`. And all 56 checks in table A, plus the loops in table B, have to change. The recompiler's fixes and hooks mechanism (`port/fixes.txt`, `port/hooks.txt`) can do both at the instruction level, without editing generated code.
- **Enemy AI:** about 40 AI functions (table B) target "the 4 party members". This supports the roadmap's plan to keep combat missions at 4–6 players and to raise the limit only in social hubs.
- **Lobby characters:** hubs probably don't need the party table to be bigger at all. Other players in a hub could be shown as separate characters ("remote avatars") without joining your party. That would leave the party (and table B) at 4 and needs a separate list of nearby players instead. This is the next thing to find out in Task 3.2.
- **Network limits:** the ad hoc matching limits (rows 2 and 3) are single instructions. Our MMO transport doesn't enforce them anyway, because the server relays. The host's connection buffers (`0x08EE0F40`, section 2) are a real 4-slot table, though: a party bigger than 4 needs it moved to a bigger allocation as well.
- **Not mapped yet:** the party HUD (it shows up to 4 entries in the live captures, apparently through the party accessors) and chat buffers were not traced to their own arrays. Hubs with remote avatars outside the party would not use either.
